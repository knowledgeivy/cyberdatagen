\section{Experimental Configuration}
\label{sec:experiment}

This section specifies the complete experimental configuration required to reproduce our evaluation framework. Following the methodology established in Section~\ref{sec:methodology}, we provide concrete parameter values for dataset composition, LLM configurations, experimental tracks, and statistical analysis procedures. Detailed hyperparameter grids, prompt templates, and cost analyses are provided in Appendices~\ref{appendix:hyperparameters}, \ref{appendix:prompts}, and \ref{appendix:costs}.

\subsection{Dataset and Sampling}

We employ the CEAS-08 spam email dataset~\cite{champa2024curated}, comprising 39,154 real-world email samples (21,842 spam, 17,312 legitimate). The corpus is partitioned into $R = 20$ independent groups through stratified random sampling, with each group containing $N = 1{,}000$ samples at fixed spam ratio $\rho = 0.1$ (100 spam, 900 ham). This 10\% imbalance reflects realistic operational conditions. An 80-20 train-test split establishes a fixed held-out test set (4 groups) held constant across all experiments, eliminating test set variance as a confounding factor. All stochastic processes employ fixed random seed (42) for reproducibility.

\subsection{LLM Models and Generation}

\subsubsection{Model Selection and Rationale}

We employ two state-of-the-art large language models: \textbf{GPT-4.1-mini-2024-04-14} (OpenAI) and \textbf{Claude-3.5-Haiku} (Anthropic). Beyond state-of-the-art generation quality, these models offer optimal cost-performance trade-offs for spam attackers (see Appendix~\ref{appendix:costs}, Table~\ref{tab:llm_costs} for detailed cost comparison). Both models provide sufficient context windows for email generation while maintaining low per-token costs, making them economically viable for large-scale spam campaigns. This selection reflects realistic attacker constraints where generation quality must balance against operational costs.

\subsubsection{Generation Parameters}

Both models employ identical generation parameters: temperature = 0.7 (balancing creativity and consistency), max tokens = 1,000, top-p = 1.0. Complete API configurations and parameter justifications are provided in Appendix~\ref{appendix:llm_config}.

\subsubsection{Prompt Engineering Strategies}

We implement three systematically varied prompt strategies to explore generation intensity: \textbf{Original} (faithful reproduction with lexical variation), \textbf{Strong} (amplified spam indicators), and \textbf{Weak} (subtle spam with reduced explicit signals). Each prompt follows a consistent JSON-formatted template ensuring reliable parsing.

\textbf{Example Template Structure:}
\begin{verbatim}
You are an expert email content analyzer. Given the
following spam email, generate a semantically similar
but lexically distinct spam variant.

[Strategy-Specific Instructions]

Original Email: {original_spam_content}

Output Format (JSON):
{"subject": "...", "body": "..."}
\end{verbatim}

\textbf{Strategy-Specific Instructions:}

\textit{Original:} "Faithfully reproduce spam characteristics including urgency signals, persuasive elements, and social engineering tactics. Introduce natural lexical variation while maintaining semantic similarity and malicious intent."

\textit{Strong:} "Amplify spam indicators by emphasizing urgency signals (limited time, immediate action), persuasive elements (too-good-to-be-true offers, authority figures), and social engineering tactics (credential requests, fake notifications). Make spam characteristics explicit and prominent."

\textit{Weak:} "Generate subtle spam with reduced explicit indicators. Create content appearing more legitimate while retaining underlying spam nature. Use professional language and minimize obvious urgency signals."

Complete prompt templates with exact wording are provided in Appendix~\ref{appendix:prompts}.

\subsection{Experimental Tracks}

Our evaluation comprises three complementary tracks systematically addressing the research questions. All experiments employ cross-group mixing strategy based on preliminary analysis showing consistent performance advantages (mean F1: 0.563 vs 0.554 for within-group, $p < 10^{-6}$, Cohen's $d = 0.13$) and better alignment with realistic deployment scenarios.

\subsubsection{Track 1: Synthetic-to-Real Detection (RQ1)}

This track evaluates whether LLM-generated synthetic spam can effectively train classifiers to detect real spam. We systematically vary synthetic data proportion $\theta$ from 0\% (pure real baseline) to 100\% (pure synthetic) in 10\% increments across both LLM models, all three prompt strategies, and 20 replications using SVM classification. Training sets contain fixed 900 ham samples with varying mixtures of real and synthetic spam ($(1-\theta) \times 100$ real + $\theta \times 100$ synthetic). All classifiers test on identical held-out real data (900 ham, 100 spam), isolating synthetic training data impact on real-world detection effectiveness.

\subsubsection{Track 2a: Baseline Detection - Real-Data-Only (RQ2a)}

This track establishes defenders' zero-shot readiness against AI-powered spam using only traditional training data. Classifiers train exclusively on real spam (900 ham, 100 spam, no synthetic exposure), then test on LLM-generated synthetic spam across both models and all prompt strategies. Both SVM and Random Forest classifiers evaluate architectural differences in detecting AI-generated spam without prior exposure. This baseline quantifies whether features distinguishing real spam from ham generalize to identifying synthetic spam.

\subsubsection{Track 2b: Enhanced Detection - Hybrid-Data (RQ2b)}

This track evaluates whether cross-model synthetic augmentation improves detection through "fighting fire with fire" strategies. Classifiers train on mixtures of real spam and synthetic spam from one LLM (training ratios: 0\%, 50\%, 100\%), then test on synthetic spam from the \emph{opposite} LLM. For example, when testing GPT-4.1-mini detection, training employs real spam augmented with Claude-3.5-Haiku synthetic samples. This cross-model design assesses whether synthetic augmentation from available LLM sources enhances readiness against attacks from different LLM sources. Both SVM and Random Forest evaluate architectural robustness across all configurations.

\subsubsection{Experimental Scale}

The complete framework comprises 2,280 training-evaluation units: 1,320 (Track 1: 2 models × 3 prompts × 11 ratios × 20 groups), 240 (Track 2a: 2 models × 3 prompts × 2 classifiers × 20 groups), and 720 (Track 2b: 2 models × 3 prompts × 3 ratios × 2 classifiers × 20 groups). This systematic coverage provides comprehensive evaluation across generation models, prompt strategies, mixing ratios, and classifier architectures with high statistical power ($>$80\% for medium effects, Cohen's $d \geq 0.5$).

\subsection{Classification Models}

We employ two widely-adopted classifiers representing distinct learning paradigms: \textbf{Support Vector Machine} (margin-based, linear kernel) and \textbf{Random Forest} (ensemble-based). Hyperparameters are optimized through systematic grid search with 5-fold stratified cross-validation on representative baseline configurations, using F1-score as the optimization metric. Track 1 employs SVM exclusively to focus evaluation on generation quality, while Tracks 2a-2b employ both classifiers to assess architectural robustness in cross-model detection scenarios.

Key findings from hyperparameter optimization: linear kernel substantially outperforms RBF for SVM (F1 = 0.825 vs 0.48-0.61), confirming appropriateness of linear boundaries for high-dimensional sparse TF-IDF features; Random Forest exhibits remarkable parameter robustness (F1 range 0.886-0.917, $<$3\% variation); SVM performance is invariant to regularization strength with linear kernel (all C values yield F1 = 0.825 ± 0.031).

Final configurations: \textbf{SVM} - C=1.0, linear kernel, balanced class weights; \textbf{Random Forest} - 100 trees, max depth=10, min samples split=5, balanced class weights. Complete grid search results and parameter justifications are provided in Appendix~\ref{appendix:hyperparameters}, Table~\ref{tab:hyperparameter_grid}.

\subsection{Feature Representation}

All emails are transformed to TF-IDF feature vectors (max 10,000 features, unigram-bigram range, standard preprocessing). The vectorizer fits exclusively on training data to prevent information leakage. This representation captures word-level and phrase-level patterns relevant to spam detection while maintaining computational efficiency. Complete TF-IDF configuration is in Appendix~\ref{appendix:feature_config}.

\subsection{Statistical Analysis}

Following Section~\ref{sec:methodology}, we compute descriptive statistics (mean, standard deviation) across $R = 20$ groups for each configuration. Paired \textit{t}-tests compare each synthetic ratio against the 0\% baseline, with Benjamini-Hochberg FDR correction ($\alpha = 0.05$) controlling false discoveries across multiple comparisons. Cohen's $d$ effect sizes distinguish statistical significance from practical importance (thresholds: negligible $|d| < 0.2$, small $0.2 \leq |d| < 0.5$, medium $0.5 \leq |d| < 0.8$, large $|d| \geq 0.8$). Linear regression models performance degradation as a function of synthetic proportion, with slope $\beta_1$ quantifying expected change per 1\% synthetic increase and $R^2$ indicating pattern linearity.

\textbf{Performance Metrics:} F1-score serves as the primary metric (harmonic mean of precision and recall, balanced under class imbalance). Supporting metrics include Accuracy, Precision, Recall, AUC-ROC, and Balanced Accuracy. Complete mathematical definitions are in Appendix~\ref{appendix:metrics}.

\subsection{Computational Infrastructure}

All experiments employ official LLM APIs (GPT-4.1-mini, Claude-3.5-Haiku) with total estimated generation cost of \$3.30 for 12,000 synthetic samples (see Appendix~\ref{appendix:costs}, Table~\ref{tab:llm_costs} for per-model cost breakdown). Classifier training and evaluation execute on standard computing infrastructure: Intel Xeon 32-core CPU, 128 GB RAM, 1 TB SSD. No specialized hardware (GPU) required. Total pipeline runtime approximately 22 hours including LLM generation (8 hours with API rate limiting), classifier training (12 hours), and statistical analysis (2 hours).
